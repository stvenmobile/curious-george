# 2026-09-19: parallel-track integration begins - repo/branch decision, and the first real MCP server

## Why parallel tracks, and why now

Concern raised directly: waiting for a fully closed autonomous loop in
this repo before starting any `piper_assistant` work risks spending too
much time fine-tuning `curious-george` before the integration that
actually matters (giving Piper a working curiosity mechanism she can act
on) gets started. Decision: run "close the loop here" and "build the
integration surface" as two parallel threads from now on, not a strict
sequence. See README.md's roadmap section for how this is reflected there.

## New repo, or a branch in `piper_assistant`?

Question: should the client-side integration work live in a new repo, or
a branch of the existing `piper_assistant` repo?

Decided: a branch in `piper_assistant`, not a new repo. The reasoning:

- The whole point of splitting `curious-george` out of `piper_assistant`
  in the first place was to get a clean validation environment, separate
  from a working, deployed assistant. That job is done - `curiosity_tools`
  is already structured (see the MCP roadmap section, predates this
  decision) to become a thin tool surface consumed from outside.
- The actual integration work is two small, separate changes to two
  already-independent repos, not a rewrite of either: `curious-george`
  gains an MCP server wrapper around `curiosity_tools` (new code inside
  this repo, not a new repo), and `piper_assistant` gains an MCP client
  plus a `LISTENING`/`RESEARCH` supervisory state machine (a branch there,
  since it's extending Piper's existing loop, not replacing it).
- A new repo would force a decision about what to "carry forward" from
  `piper_assistant` - its deployment tooling, hardware drivers, existing
  state machine - real duplication risk for no real benefit, since
  `piper_assistant` isn't being started over. A fresh repo would only make
  sense if the plan were to rewrite Piper's core loop rather than extend
  it, which isn't the plan.

## The first real MCP server

Built `curiosity_tools/mcp_server.py` - not a sketch, a real server using
the `mcp` SDK's current (v2) `MCPServer` API. Notable: `mcp` 2.x renamed
`FastMCP` to `MCPServer` (different import path,
`mcp.server.mcpserver.MCPServer`) - most existing examples online still
show the old v1 `FastMCP` shape, which raises a clear `ModuleNotFoundError`
pointing at the migration guide rather than failing silently. Worth
knowing before searching for MCP server examples again.

Design, following the two architectural differences the README already
named as the transition's real cost (not discovered new today, just acted
on for the first time):

- **Warm vs. fresh, deliberately not applied uniformly.** The server loads
  exactly one base model + tokenizer + embedder at startup and keeps them
  warm for the process lifetime - but only for the cheap, single-forward-
  pass operations (`add_candidate_topic`'s baseline loss reading and
  embedding). `run_deep_scoring` and `study_topic` still reload a fresh
  base model per trial internally, unchanged, exactly as `deep_scoring.py`
  and `study.py` already document and already do outside the MCP wrapper.
  That's deliberate, not a gap: those reloads exist for clean measurement,
  and "make everything warm" would silently change what deep-scoring
  trials actually measure. The wrapper draws the warm/fresh line exactly
  where the existing code already drew it, rather than picking a new one.
- **Service shape, not library shape.** Every tool takes and returns plain,
  JSON-serializable data (topic names, content strings, floats, dicts) -
  never a live model/tokenizer/embedder object. `MemoryItem`/
  `DeepScoreRecord` dataclasses and `loss_history`'s tuples get an explicit
  serialization step (`_serialize_item`) rather than crossing the
  boundary as-is.

Tools exposed today: `list_topics`, `get_topic` (introspection - store-only,
no live model needed, so these are the only tools with a fast, non-mocked
test), `add_candidate_topic`, `run_deep_scoring`, `rank_active_topics`,
`study_topic` - i.e. today's whole manual pipeline, each one a thin
pass-through to the function that already existed. Deliberately does NOT
expose a `research_trigger` tool yet - that policy (candidate capacity
rules, what "what to research"/"intended duration" mean, breadth-then-depth
selection) is still an open design question from 2026-09-16's session, not
resolved today, and building a placeholder policy just to fill out the MCP
surface would mean building it twice. The primitives being real and callable
today is what unblocks `piper_assistant`'s client side from starting now,
without waiting on that design to land first.

## What's still open

The RESEARCH trigger's design questions from before this session are
unchanged and still block a `research_trigger` tool specifically (not the
rest of the server): pipeline-capacity tier (candidate vs. active) and
whether a `PipelineStatus.SHELVED` value is needed, what "what to research"
and "intended duration" mean as real parameters, and the breadth-then-depth
selection policy's two sub-questions (what counts as "breadth achieved",
and whether newbie-phase selection should be resonance-weighted or strict
rotation). Next real step on the `curious-george` side is resolving those,
not further MCP-surface work - the surface is complete for what's already
built.
